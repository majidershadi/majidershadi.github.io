SmartPath DNS: Engineering an Adaptive Local Resolver for Unreliable Networks

How I designed a local DNS control plane that races multiple resolver paths, learns from real traffic, preserves useful answers, and keeps every expensive feature bounded and optional.

Published August 20, 2026Last technically verified August 20, 2026By Majid Ershadi

Scope and date. This article documents the SmartPath DNS architecture and implemented behavior as of August 20, 2026. Ghosting is an optional feature and is disabled by default. The project is a forwarding resolver and local control plane; it is not an authoritative DNS server and does not recursively walk the public DNS root hierarchy.

I started SmartPath DNS because changing a laptop or router from one public resolver to another should not be the operational response to an unstable internet path.

On a healthy network, resolver choice can look trivial. Configure one familiar address—perhaps Cloudflare, Google, Quad9, Control D, or an ISP resolver—and forget about it. On an inconsistent network, that assumption breaks. A resolver may be reachable over classic UDP but unreliable over TLS. A DNS-over-HTTPS endpoint may succeed while port 53 is degraded. One provider may answer quickly for a period and then become the slowest path. Two resolvers may return different address sets for the same name because they see different CDN topology. An ISP may interfere with, redirect, throttle, or simply mishandle one protocol while another continues to work.

The practical problem was not “which public DNS provider is universally fastest?” There is no permanent answer to that question. The problem was:

How can a local resolver continuously choose the best available path for this network, for this moment, without hiding its decisions or consuming unlimited resources?

SmartPath DNS is my answer. It is written as a fast Go service with a persistent SQLite/WAL state layer and a hands-on web control plane. It accepts ordinary DNS over UDP and TCP on the local machine, forwards queries through a configurable collection of classic DNS, DNS-over-TLS, and DNS-over-HTTPS upstreams, and learns from the observed latency and reliability of every path.

Design goals and explicit non-goals

The design began with a set of concrete goals.

  • Survive partial network failure. Losing one provider or protocol must not immediately break local name resolution.
  • Make selection adaptive. Resolver ordering should reflect measured behavior, not a static opinion embedded in configuration.
  • Keep the common path fast. Cache hits must remain local and expensive comparison features must be bounded.
  • Support encrypted and classic transports. UDP, TCP, DoT, and DoH are independent network paths and should be usable together.
  • Preserve learning across restarts. Container recreation must not erase cache records, weights, profiles, settings, or telemetry.
  • Expose the decision process. A local infrastructure service should show its upstreams, waves, latency, cache, failures, and current limits.
  • Default to safe optional behavior. GEO lookups, HTTP endpoint probes, external intelligence services, and Ghosting all create additional traffic and must require deliberate activation.
  • Bound resources. Concurrency, candidate count, timeouts, database size, history retention, and background discovery must all have user-controlled limits.

There are also deliberate non-goals. SmartPath does not replace authoritative DNS, DNSSEC validation policy at a validating resolver, enterprise split-horizon architecture, or a dedicated filtering product. It does not promise that the first answer is always semantically superior. It does not assume geolocation is truth. It does not make an unstable network stable; it makes local DNS resolution more resilient to instability in individual paths.

Architecture: a small data plane and an observable control plane

The Go engine owns authoritative application state. The browser is not the source of truth. Settings, learned upstream measurements, cache records, query telemetry, profiles, Ghosting jobs, and discovered names are stored in SQLite. The dashboard reads and changes those records through a versioned local API. This means closing the browser does not pause learning, and restarting a container does not reset the system.

Hot cache entries also live in memory. SQLite is consulted when the process has restarted or the memory layer misses. This hybrid design avoids a disk query for every common cache hit while retaining durable state.

The complete query lifecycle

A normal query passes through a deliberately ordered pipeline.

1. Validate and normalize

The current engine accepts one DNS question per request. The cache key normalizes the fully qualified name and includes record type, class, and the DNSSEC OK bit. Including the DO state avoids incorrectly serving an ordinary cached response where the client requested DNSSEC-related data.

2. Check the local cache

The memory cache is checked first. A fresh match is copied, its TTLs are aged, the original request ID and question are restored, and the answer is returned immediately. If memory misses, SQLite can restore a persisted answer. Cache hits never need to enter an upstream race.

3. Build priority waves

Enabled upstreams are partitioned into a high-priority first wave and a low-priority fallback wave. Privacy mode excludes unencrypted UDP and TCP upstreams. SmartPath protects a configurable minimum high-priority population—five by default—so learning cannot gradually demote every useful racer into the fallback set.

4. Race the first wave

First-wave upstreams are launched concurrently, subject to the global parallel-task ceiling. Each exchange shares the query’s total timeout. This is important: concurrency control is not permission to let queued work live forever. If a task waits too long for a slot, the original DNS deadline still wins.

5. Hedge with a second wave

A timer controls the low-priority hedge. If no valid first-wave result arrives before the configured delay, the second wave joins. If the first wave already produced a usable answer, unnecessary low-priority work remains suppressed. The fallback wave is therefore available for resilience without becoming a mandatory cost for every query.

6. Decide how much evidence is enough

First-response and privacy profiles return the first valid response. Smart and GEO modes open a short decision window after the first usable answer so alternatives can be compared. A valid terminal result is either NOERROR or NXDOMAIN; an empty successful answer can be meaningful and is not automatically treated as transport failure.

7. Select, learn, cache, and respond

The fastest accepted upstream receives a win and a weight increment. Smart selection may reorder address records after endpoint or GEO comparison. The final message keeps the client’s ID and original question, enters memory and persistent cache, is logged according to the configured privacy setting, and is returned.

Four upstream transports, one common result model

SmartPath treats each configured protocol endpoint as an independent path, even when several paths belong to the same provider.

TransportImplementation concernWhy it matters
DNS over UDPLow overhead, port 53, possible fragmentation or interferenceOften the fastest path, but commonly affected by restrictive networks
DNS over TCPConnection setup and stream framingUseful when UDP is unavailable or responses are large
DNS-over-TLSTLS 1.2+, certificate and server-name validation, usually port 853Provides an encrypted DNS channel with explicit DNS semantics
DNS-over-HTTPSRFC 8484 DNS wire messages over HTTPS, HTTP status and body limitsCan survive networks where dedicated DNS ports are degraded

The built-in configuration provides twelve paths across Cloudflare, Google, Quad9, AdGuard, Mullvad, and Control D Unfiltered. Control D is represented by both of its unfiltered legacy IPv4 addresses, its DoH endpoint, and its DoT bootstrap path with the correct TLS name. Presets are ordinary records after seeding: users can test, disable, move, edit, add, and remove endpoints. A deliberately deleted preset is not silently recreated on every restart.

DoH is sent as DNS wire format rather than a provider-specific JSON shortcut. DoT and DoH validate TLS identities. Transport failures are recorded separately from valid DNS response codes so a name that genuinely does not exist does not damage a resolver’s reliability score.

Learning without destroying fallback capacity

Adaptive systems become dangerous when “learning” is an opaque label for uncontrolled state changes. SmartPath uses intentionally understandable signals.

Each attempted upstream records latency, query count, failure count, last-seen time, wins, and a learned weight. Average latency is an exponentially weighted moving average: new measurements influence the score without completely replacing history. A winning path gains weight; a non-winning attempt decays slightly. Reliability is calculated from successful and failed attempts.

Periodic rebalancing compares sufficiently sampled upstreams. A resolver can move to the low-priority wave when its average latency is far above the learned group average by the configured demotion factor. Rebalancing refuses to violate the minimum high-priority count. This creates a crucial invariant:

Learning may change preference, but it may not learn the system into having no first wave.

The dashboard exposes every component of this process: observed latency, reliability, queries, failures, wins, weight, score, enabled state, and assigned wave. An operator can reset learning, force rebalancing, test one upstream directly, or move it manually.

When DNS answers are not equivalent

Different resolvers can legitimately return different address sets. CDN mapping, anycast topology, ECS behavior, cache age, and provider policy can all influence the result. SmartPath supports two optional comparison mechanisms.

HTTP or HTTPS endpoint probing

When enabled, SmartPath extracts unique A and AAAA candidates and probes the configured path using the original hostname. Preserving the hostname and TLS server name matters because connecting to an address without the intended virtual host can measure the wrong service or fail certificate validation. The probe is bounded by its own timeout. The fastest one or two addresses—configurable by the user—are retained while CNAME and other non-address records remain intact.

This feature is disabled in profiles where its extra outbound traffic or latency is undesirable.

GEO consensus

GEO-aware mode can ask several editable location providers about the local resolver, an address, or a domain. Domain targets are first resolved to every A and AAAA address and then evaluated through enabled address providers; direct-domain sources can also participate. SmartPath chooses the country by provider consensus and averages coordinates among agreeing observations before ranking candidate addresses by distance.

Geolocation is advisory, not an authorization decision. Sources can disagree, rate-limit, fail, or return approximate coordinates. The dashboard therefore shows each observation and its error rather than presenting a single country label as unquestionable truth. GEO lookup is disabled by default and successful consensus is cached for a configurable period.

Persistent cache as an availability layer

The cache is not merely a speed optimization. On a network where upstream access intermittently disappears, a recent local answer can be the difference between a degraded session and a complete outage.

SmartPath applies a configurable multiplier to upstream TTLs and constrains the result between minimum and maximum limits. Positive answers, negative answers, and stale eligibility are represented explicitly. Truncated responses are not cached. On an upstream failure, a stale entry may be served within the configured stale-on-error window.

Every cached message stores:

  • the normalized cache key and queried name;
  • record type;
  • packed DNS response bytes;
  • fresh expiry and stale-until timestamps;
  • original storage time and effective TTL;
  • winning source; and
  • local hit count.

The hit count is operationally useful. It allows the storage manager to distinguish a frequently reused record from a cold record that was cached once and never requested again.

Resource guardrails: parallel work and database growth

A resolver that races many providers can accidentally multiply work. Five upstreams times one query is reasonable. Five upstreams times hundreds of simultaneous client queries—plus background prefetching—can become a socket, CPU, memory, and bandwidth problem.

SmartPath therefore has a live global parallel-task limiter. It bounds simultaneous upstream exchanges across ordinary client queries and Ghosting prefetches. The limiter can change while the process is running. Waiting tasks wake when the limit increases or another task releases a slot. The dashboard reports the active count, current ceiling, and observed peak.

Storage is bounded as well. The operator chooses a database budget from 8 MB to 10 GB and a rotation target between 50 and 95 percent. When active SQLite data crosses the limit, maintenance performs this sequence:

  1. delete DNS cache records whose stale window has expired;
  2. measure active pages again;
  3. select cache rows ordered by lowest hit count and oldest storage time;
  4. delete bounded batches until active data reaches the target or no cache rows remain;
  5. checkpoint the WAL and request incremental vacuuming; and
  6. persist the rotation timestamp and cumulative number of cold records removed.

New databases enable incremental vacuum mode. Older SQLite files may retain freed pages as allocated but reusable space. That is not lost capacity: SQLite consumes those pages before extending the file again. The dashboard distinguishes active data, allocated bytes, and reusable pages so “file size” is not confused with “live records.”

Enforcement runs after settings changes, once per minute during maintenance, and on demand through the dashboard or API.

Ghosting is an optional prefetch feature

Ghosting explores a different question: can the resolver prepare likely related names before an application asks for them?

It is deliberately implemented as a feature, not as a requirement of the DNS path. Ghosting is disabled by default. Enabling it is an explicit decision because it can generate additional DNS, HTTPS, and third-party API traffic. Manual runs are also explicit and visible.

A Ghosting job can use four independently controlled waves:

WaveTechniqueBoundary
DNS relationsFollow CNAME, MX, NS, SRV, SVCB, and HTTPS targetsOnly names under the same registrable root are accepted
Landing pageFetch the root over HTTPS and inspect link, source, and form targetsRedirects remain in scope; private, loopback, and link-local destinations are blocked
Passive intelligenceCertificate transparency and optional free or paid subdomain servicesHTTPS-only provider URLs, bounded responses, timeouts, and environment-only secrets
DictionaryTry an editable set of labels such as api, cdn, or authDisabled by default and constrained by candidate and concurrency limits

Presets include crt.sh, HackerTarget Host Search, Cert Spotter, VirusTotal, and SecurityTrails. Providers can be disabled individually. Paid API values are read from named environment variables and are never stored in the dashboard settings or SQLite database.

Discovered names are resolved through the same SmartPath engine and placed into the normal persistent cache. Ghosting’s own queries are not counted as user traffic and cannot recursively start more Ghosting jobs. Jobs, warnings, discoveries, source, wave, answer count, latency, and cache-warm result are persisted. A running job can be stopped and its history can be cleared independently of the DNS cache.

The feature has separate controls for maximum candidates, concurrent warmups, HTTP/API timeout, delay between waves, automatic refresh cooldown, record types, dictionary entries, and provider list. This is important because prefetching is useful only while it remains subordinate to real queries.

Security and privacy boundaries

A local DNS control plane observes sensitive metadata and initiates network requests, so its security model cannot stop at transport encryption.

Local exposure

The supplied Docker configuration binds the dashboard, API, and DNS listener to loopback. Exposing the API beyond the local host requires an explicit configuration change. An optional API key protects non-health endpoints through the X-SmartPath-Key header. The dashboard should sit behind a local authenticated reverse proxy if the API key is enabled for browser use.

Secret handling

DoH and DoT server names are configuration, not secrets. Paid intelligence API keys are secrets and remain process-level environment values. Exports include settings and provider environment-variable names, not the secret values.

Outbound request safety

Landing-page Ghosting resolves destinations itself and accepts only public global-unicast addresses. It rejects private, loopback, and link-local targets and prevents redirects from leaving the registrable domain. Passive-intelligence endpoints must use HTTPS and use the same public-destination transport. Response bodies and request time are limited.

Query privacy

The privacy profile restricts forwarding to encrypted DoT and DoH paths and can redact domain names in new query-history rows. This does not make DNS activity invisible to the selected resolver or destination network. It narrows local logging and protects the forwarding channel; it is not anonymity.

Fail-closed validation

Settings are validated before persistence. Timeouts, sizes, concurrency, candidate count, TTL range, modes, provider templates, protocols, and DNS labels have explicit bounds. Invalid settings do not partially apply.

Profiles and the web control plane

SmartPath includes predefined operating profiles because one set of tradeoffs does not fit every connection.

  • Balanced uses smart comparison with practical default limits.
  • First response minimizes the decision window and returns one address quickly.
  • Deep learning gathers more evidence and enables endpoint probing.
  • Privacy uses encrypted upstreams and redacted query history.
  • GEO aware enables location consensus and proximity preference.

The dashboard is not a decorative status page. It provides:

  • live latency, QPS, cache-hit rate, and recent query activity;
  • high- and low-priority upstream tables with test, move, enable, and delete controls;
  • cache search, individual removal, full clearing, and JSON export;
  • profile activation and detailed resolution settings;
  • editable GEO sources with a consensus tester;
  • Ghosting configuration, live waves, jobs, discoveries, stop, and cleanup;
  • parallel-task activity and database-budget telemetry; and
  • pause, resume, rebalance, and learning-reset actions.

The API is versioned under /api/v1. The dashboard uses a same-origin proxy to avoid exposing engine topology to client code. API and dashboard state are intentionally separate from the DNS packet listener so the resolver can continue serving while no browser is open.

Deployment on Windows, macOS, and Linux

The engine and dashboard run either in Docker or through native Go and Node workflows. Docker Compose is the recommended local scenario on Windows.

docker compose up --build -d

# Supplied Windows-safe dashboard binding
Start-Process "http://localhost:13000"

# Verify containers
docker compose ps

The named smartpath-dns-data volume stores SQLite data independently from container lifetime. A normal docker compose down preserves it. Deleting volumes is intentionally documented as a separate destructive choice.

DNS binds to 127.0.0.1:53 in the supplied Compose configuration. The operating system can then use the local address as its resolver. Windows uses Set-DnsClientServerAddress; macOS can use networksetup; systemd-resolved systems can use resolvectl. Port 53 may already belong to another local stub, VPN client, security product, or container platform, so the owner should be identified before changing system DNS.

Native development defaults to unprivileged port 10053. Binding port 53 on Unix-like systems should use the narrowest available capability rather than running the entire service as root.

Verification strategy

The implementation is tested at several layers.

  • Resolver unit tests cover cache-key isolation, TTL scaling, alias preservation, answer limiting, and local upstream races.
  • GEO tests use controlled providers to verify multi-source consensus.
  • Limiter tests prove that a waiting task cannot exceed the current ceiling, that a live limit increase releases work, and that canceled contexts do not acquire slots.
  • Storage tests build a SQLite database above its configured budget, verify cold-record rotation, and confirm a frequently-hit cache entry survives.
  • Ghosting tests cover public-suffix scoping, provider parsing, dictionary bounds, persistence, and cache warming.
  • Dashboard validation includes linting, production compilation, and server-rendered HTML checks.
  • Docker smoke tests verify service health, same-origin API proxying, persistence through engine recreation, and real DNS resolution through 127.0.0.1:53.

Testing a resolver only with a successful example.com lookup is not enough. The important cases are partial answers, timeouts, cancellation, cache aging, stale behavior, encrypted transport validation, differing address sets, resource pressure, persistence, and operator error.

Operational guidance

A practical starting configuration is intentionally conservative:

  • keep at least five healthy first-wave paths across more than one provider and protocol;
  • use a total DNS timeout that matches the actual network rather than an arbitrary large value;
  • keep the second-wave delay shorter than the total timeout;
  • begin with the global parallel-task default and lower it only when resource pressure requires it;
  • set a database budget that leaves operating-system and container-volume headroom;
  • enable endpoint probing only when selecting between returned addresses is worth the added requests;
  • enable GEO only when proximity is meaningful for the workload;
  • leave Ghosting disabled until its additional discovery traffic is understood and desired;
  • review provider terms and rate limits before enabling passive intelligence services; and
  • export configuration before major upgrades and preserve the Docker volume.

Weights should not be treated as permanent truth. A network change, VPN, ISP routing event, travel, resolver incident, or protocol restriction can invalidate yesterday’s measurements. SmartPath keeps learning because the path is the variable.

Lessons from building SmartPath

The most important lesson is that resilience comes from controlled diversity, not from maximizing concurrency.

Querying every possible provider all the time would create traffic without judgment. Depending on one provider would eliminate the very diversity needed during a path failure. The two-wave model is the balance: enough simultaneous alternatives for a fast decision, a delayed reserve for failure, and learning that changes membership without destroying minimum capacity.

The second lesson is that caching policy is operational policy. Extending a TTL can improve availability but preserve an outdated destination. Serving stale can rescue an outage but should have a clear limit. A database can preserve knowledge but must rotate cold data. Every cache feature is a tradeoff, so each one is visible and adjustable.

The third lesson is that optional intelligence must remain optional. GEO, HTTP probing, certificate transparency, passive APIs, landing-page inspection, and dictionary discovery can all add useful context. They also add requests, privacy implications, rate limits, and failure modes. Ghosting therefore remains a bounded feature that is disabled by default—not a hidden side effect of asking a DNS question.

The fourth lesson is that an adaptive service needs an explanation surface. Operators should be able to answer: Which upstream won? Which paths are currently slow? Why is this resolver in the second wave? Was this answer cached? How much concurrency is active? How much database capacity is reusable? Which Ghosting source discovered this host? A dashboard is valuable when it answers operational questions, not merely when it looks polished.

Current limitations and future direction

SmartPath is useful today, but several areas deserve continued work.

  • Full DNSSEC validation could become an explicit local policy rather than relying on upstream behavior.
  • Per-domain or per-network upstream preference could complement global provider learning.
  • Additional cache admission policy could prevent one-time bulk queries from displacing broadly useful records.
  • Prometheus or OpenTelemetry export could integrate the engine into larger monitoring systems.
  • Signed configuration backups and restore workflows could improve operational recovery.
  • Router-oriented packages could make deployment easier outside workstations.
  • More passive discovery providers could be added through the existing generic parser while preserving strict scoping and limits.
  • Network-change detection could reset or segment learning when a device moves between materially different connections.

These additions should follow the same rule as the current system: no hidden unbounded work, no unexplained state, and no optional external traffic enabled by surprise.

Final reflection

SmartPath DNS began with a recurring operational frustration: an internet connection could be working while one DNS path made the entire system feel broken. Changing resolver addresses manually solved one moment and created no memory for the next.

The project turns that manual reaction into a local control loop. It measures actual paths, races only within explicit limits, keeps a fallback wave, preserves useful answers, learns without eliminating minimum capacity, and makes its internal state visible.

The deeper principle extends beyond DNS:

When infrastructure depends on external paths that can fail independently, resilience comes from observable diversity, bounded competition, durable local knowledge, and safe fallback.

That is the architecture SmartPath DNS is designed to provide.
