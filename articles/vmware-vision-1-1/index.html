VMware Vision 2.0.1: A Practical VMware Activity Trail in Splunk

Follow recorded VM changes, put parsing on the right tier, and configure data models without confusing requests, diagnostics and completed operations.

Published September 17, 2026Release examined: 2.0.1 · Updated October 16, 2026By Majid Ershadi

A useful VM audit starts with a few questions: which VM changed, who changed it, when, and what was the outcome? Service logs can help an investigation, but their volume can hide the records that answer those questions.

VMware Vision 2.0 changes how the application processes that data. Native configuration in the technical add-on replaces the automatic Python lookup used by earlier versions. The main Overview reads a small set of indexed fields through one shared tstats search. Detailed investigations and older raw data use native field extraction.

This article was first published for 1.1 and is updated for 2.0.1. The app still uses existing vCenter, ESXi and Aria syslog. It does not poll VMware APIs, collect live inventory or change VMware settings. API collection may be considered in a future release; no API collector is included now.

Why the 2.0.1 patch matters

A review of 2.0.0 found cases where indexed and detailed results disagreed. This patch aligns failure handling, removes JSON property-order filtering, checks fragment numbers in the header, handles quoted event types and plain syslog envelopes, and restores login source IP and task ID fields.

Upgrade both packages. Corrected arrivals use vv_schema=2.0.1. Overview intentionally excludes older vv_schema=2 records because their stored metadata may be wrong. Use Historical Activity and native detailed searches for that period. The upgrade preserves raw data and does not automatically replay or reindex it. Rebuild affected accelerated VMware/CIM summaries after the search rules are deployed. The patch migration guide includes deployment, verification and rollback steps.

What the events can tell you

The app follows supported VM creation, removal, power, configuration, migration and snapshot events, plus users, failures and operational context. A requested action does not establish a completed outcome. Last observed state describes received history; it is not current inventory.

Version 2.0 corrects the supplied name-first power messages and Message-on VM names, keeps event IDs separate from nested configuration keys, and extracts Modified/Added/Deleted details when present. InventoryMonitor messages that merely mention an event class no longer establish a completed power-off or CIM Change.

Multi-part and incomplete bracketed records are marked partial. Header identity and available text remain inspectable, but the record does not establish a complete change or enter CIM Change. Automatic cross-record reassembly is not implemented. It requires reliable source, event and fragment information; timestamp proximity alone is insufficient.

Choose the sources deliberately

vCenter event records are the primary audit source. ESXi adds host and local operational context. Aria can relay VMware records, but its own appliance service logs are not a complete VM audit history. Verify the actual event format, source timestamp and original origin at the receiver.

Keep raw diagnostic traffic available for troubleshooting. A large unmapped percentage alone is not proof of lost data or inaccurate VM history. Missing identity on a real VM event deserves investigation. Avoid forwarding the same event through multiple routes unless duplicate-delivery behavior is understood.

The app and technical add-on

Component Responsibility Placement
VMware Vision app 2.0.1 Dashboards, custom models and the UCC logging page Search heads
TA-vmware-vision 2.0.1 Native ingest classification, field extraction, CSV event mapping and CIM tags First full parser and search heads

Install both packages on standalone Splunk. Search heads now require the TA too. If an HF first parses raw syslog, apply the TA there. If indexers first parse the raw input, deploy it there instead. Already cooked data does not need a second parsing pass downstream. The TA on search heads distributes search knowledge to peers; that bundle does not configure upstream ingestion.

Configure the TA

  1. Record the collection route, indexes, sourcetypes and search-role permissions. Back up both existing apps, local settings and local metadata before upgrading.
  2. Download the two 2.0.1 installation archives and verify the release's SHA256SUMS.txt. The GitHub source ZIP is not a Splunk install package.
  3. Deploy the TA to the first full parser and search heads. Use the cluster manager for an indexer cluster and the deployer for a search head cluster. Install the full app on search heads.
  4. Keep existing listeners, file monitors, forwarding and index definitions in their managed collection apps. Neither package enables collection or creates indexes.
  5. Assign vmware:vision:vcenter, vmware:vision:esxi, vmware:vision:aria or vmware:vision:json as appropriate. Typed JSON needs supported explicit event fields; assigning a VMware sourcetype cannot create missing source content.
  6. Review local 1.x props, transforms, fields and metadata overrides. The app supplies empty retirement settings for LOOKUP-vmware_vision; a local rule can override them and keep the old Python lookup active.
  7. Apply the normal configuration restart/reload procedure at the affected tiers. Check the effective native rules with btool and confirm bundle replication on every search peer.
/opt/splunk/bin/splunk btool props list vmware:vision:vcenter --debug
/opt/splunk/bin/splunk btool transforms list vv_event_map --debug
/opt/splunk/bin/splunk btool fields list vv_schema --debug
/opt/splunk/bin/splunk btool check

The TA has no Python runtime dependency or API credentials. The app's UCC Python runtime supports its configuration page, independently of event parsing. Follow the TA guide and migration procedure for deployment and rollback.

Install and check the first records

Set vmware_vision_indexes in Settings → Advanced search → Search macros. A definition such as (index=vmware-vcenter OR index=vmware-esxi OR index=log-insight) scopes the app. Ensure roles can read each index.

New arrivals through the TA receive five indexed fields: vv_schema, vv_record_class, vv_event_type, vv_vcenter and vv_failure. Large change bodies and arbitrary VM attributes are not custom indexed fields. Raw content is preserved.

| tstats count WHERE index=vmware-vcenter vv_schema="2.0.1"
  BY vv_record_class vv_event_type vv_vcenter

The main Overview covers those new schema-2.0.1 records. It can be empty immediately after an upgrade even when older raw data exists. Open Historical Activity for old data and native detailed searches. No automatic backfill or reindexing occurs. Compare a known VM operation with its raw record in both VMware Vision and Search & Reporting.

The indexed view counts received records, including duplicates. Historical audit panels may deduplicate by available event identity. Those totals have different meanings. Review the indexed event-hour coverage before relying on the view.

Set up the VMware data models

The app provides detailed VMware_Vision and compact VMware_Vision_Activity models. Both use the VMware index macro and native fields supplied by the TA. CIM is not required for these custom models. The main Overview uses indexed fields directly and does not require acceleration.

| datamodel VMware_Vision Events flat strict_fields=false
| table _time vcenter vm_name event_type vmware_action status
| head 30

For optional Activity acceleration, open Settings → Data models, select VMware Vision Activity, then Edit → Edit Acceleration. Start with a suitable short summary range, observe scheduler/storage cost and wait for coverage. Use the separate Accelerated Activity dashboard after checking summaries.

| tstats summariesonly=true count
  FROM datamodel=VMware_Vision_Activity.Activity
  BY Activity.vmware_action

Summary-only searches omit unsummarized data. Summary range is separate from raw retention. Rebuild affected summaries after migration so they reflect corrected extraction and exclusions. Acceleration does not repair incorrect source classification or incomplete messages. See the model guide.

CIM and Enterprise Security

The TA maps explicit login outcomes into Authentication and selected VM lifecycle/configuration/power/migration/snapshot outcomes into Change. Native operation names remain in vmware_action; eligible records use standard CIM values in action. Requests, logout, unknown event types, generic diagnostics and partial records are outside these initial mappings.

Install the CIM version supported by your Splunk/ES deployment. In /en-US/app/Splunk_SA_CIM/cim_setup, add the VMware indexes to Authentication and Change's allowlists while preserving other source indexes. The equivalent macros are cim_Authentication_indexes and cim_Change_indexes. These are independent of vmware_vision_indexes.

| datamodel Authentication Authentication flat strict_fields=false
| search sourcetype=vmware:vision:*
| stats count by action app

| datamodel Change All_Changes flat strict_fields=false
| search sourcetype=vmware:vision:*
| stats count by action status change_type

Run these as separate searches. Verify source eligibility, tags and each ES detection's required fields before enabling summaries. Missing client IP, object ID or before/after detail is not invented. See the CIM guide.

Understand coverage results

Label Meaning
lookup_missing or MISSING A dashboard/search placeholder for absent normalization metadata; check TA knowledge, overrides and peer deployment.
unclassified / unmapped No supported format was recognized. Inspect examples before deciding whether they are routine output or a missing useful event.
unmapped_event_type An explicit event class has no mapped operation; success is not inferred.
diagnostic A recognized service message. It can still report an important service failure.
partial_event / fragment Multi-part or incomplete bracketed content; excluded from complete-event audit and CIM Change.
identity_quality=missing No usable identity was extracted; compare the source, supported patterns and ambiguity.
mapped A mapping was selected. Validate the VM, actor and outcome against the original record.

The 1.1.1 post-release findings remain documented in its historical release notes. Version 2.0 fixes the reproduced patterns through the native path, but does not claim every VMware log format is supported. Useful audit accuracy takes priority over classifying every diagnostic.

Upgrades and common problems

If the indexed Overview is empty, check new-arrival vv_schema=2.0.1 metadata at the first parser. If native fields are absent, check the TA on search heads and peers. If Python event normalization still runs, inspect local overrides of the retired automatic rule. If detailed raw searches are slow, narrow time/index/VM filters and use the indexed aggregate view where its coverage fits.

The old scripted CSV lookup's CRLF-matching path is removed from routine processing. CRLF is not required by the application, and no sender setting is changed. Validate actual multiline boundaries and retained raw text. Native extraction cannot restore content already lost or safely join arbitrary fragments.

Rollback restores both packages and their local settings through the same deployment mechanism. Existing indexed metadata remains stored; do not delete raw indexes. Historical indexed fields would require a separately planned reingestion project, while native historical extraction requires no reindex.

Build and validation

git clone https://github.com/majidershadi/vmware-vision.git
cd vmware-vision
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-build.txt
make release

Build on Linux/WSL with Python 3.10 or newer, Git and GNU Make. UCC 6.6.0 builds the app; the TA generator packages native configuration. Development scripts, reference decoder, tests, credentials and lab data are excluded from install archives. See the build guide.

The patch is checked on standalone Splunk 10.4.1 with CIM 8.7.0. The test suite has 67 offline checks and 40 synthetic live cases covering native fields, indexed classifications, dashboard filters and raw preservation. Separate checks cover VMware/CIM model membership and the old-schema fallback. Full acceptance evidence is attached to the release. These tests do not certify a distributed production topology.

The earlier 2.0.0 controlled 5,000-record comparison had median job durations of 0.108 seconds with native fields, 0.782 seconds when adding the explicit legacy Python lookup, and 0.040 seconds with indexed tstats. One indexed trial took 1.264 seconds. The source format was a single common event shape with distinct header IDs; lookup-cache reuse was avoided for the legacy comparison. These figures demonstrate the tested paths, not production capacity or a guaranteed response time. Those timing samples remain attached to the 2.0.0 release; they are not a new 2.0.1 performance claim.

Native Linux AppInspect found no errors, failures or future failures. The app retains ten advisory warnings; the TA has none. Local inspection is not Splunkbase or Cloud approval. Splunk 10.0.2 distributed acceptance, real sender delivery, ingest queues, index growth and production concurrency still need checks in the target topology. The release remains beta.
