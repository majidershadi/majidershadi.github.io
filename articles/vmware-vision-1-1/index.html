VMware Vision 1.1.1: A Practical VMware Activity Trail in Splunk

Follow recorded VM changes, put parsing on the right tier, and configure data models without confusing requests, diagnostics and completed operations.

Published September 17, 2026Release examined: 1.1.1By Majid Ershadi

A VM has changed, and the first questions are usually simple: what happened, when did it happen, and who did it? The answer is often spread across vCenter events, ESXi messages and a syslog relay. A search for the VM name helps, but it also brings back service messages, task requests and repeated copies of the same event.

VMware Vision puts those recorded events into a usable activity trail in Splunk. Version 1.1.1 covers VM creation, removal, power operations, configuration changes, migration and snapshots, together with related users, failures and infrastructure events. It includes dashboards, two custom data models and scoped mappings into CIM Authentication and Change.

This release works with logs you already collect. It does not poll vCenter, ESXi or Aria APIs. API collection may be added in a future release, but there is no schedule or API collector in this version. The application also does not maintain a complete live inventory or change VMware settings.

Source and documentation · Installation packages

What the events can tell you

The overview shows recent activity, users and failures. VM History follows an individual VM through recorded events. Configuration and Change Audit shows changes when the source supplies the details. Operations and Security brings together authentication, permissions, alarms, host events and tasks. Setup and Coverage helps explain missing fields and unmapped records.

The distinction between a request and an outcome matters. “Starting VM” is a request; it does not prove that the VM powered on. A failed power-on must not become the last successful power state. The parser keeps these records separate. Likewise, a snapshot event can show that a snapshot operation happened without containing the snapshot's own identifier.

VM identity prefers a UUID or a vCenter-scoped managed object ID. A name alone is weaker because names can change or be reused. Last observed state means the last relevant successful event in the available history. It is not a fresh inventory reading.

Choose the sources deliberately

SourceWhy collect it?What to watch for
vCenterThe main source for VM lifecycle, changes, actors and event outcomes.Forward actual event records as well as the service logs needed for troubleshooting. A large volume of vpxd messages does not guarantee a complete audit trail.
ESXiHost and local operational context, particularly when investigating activity outside vCenter.Host messages do not always contain a VM identity or the user responsible for a change.
AriaA collection or forwarding path, and appliance operational context.Preserve the original event, timestamp and source. Aria's own diagnostics are not a substitute for vCenter events.

A routine ResourceModel.queryBatch call or an activation check is normally a diagnostic message. Assigning a made-up VM operation to every such line would make coverage look better while making the audit trail less reliable. Diagnostic records remain searchable, but they do not belong in VM change counts.

If Aria forwards the same vCenter records that arrive through another route, expect duplicates. Keep a single delivery route where practical, or understand how the totals differ: some audit panels deduplicate event identity, while data-model summaries count received records.

The app and the technical add-on

There are two installation packages. The full vmware_vision app, version 1.1.1, supplies search-time normalization, dashboards, reports, models and CIM mappings. TA-vmware-vision, version 1.0.2, supplies event boundaries, timestamp settings and character encoding for the raw parsing tier.

VMware syslog → collector → heavy forwarder → indexers
                              ingestion TA       ↑
                                                 │ search bundle
                                            search head
                                         VMware Vision app
DeploymentPackage placement
Standalone SplunkInstall the full app. It already includes the parsing settings.
Heavy forwarder first parses raw syslogInstall the TA on that HF and the full app on the search head. Downstream indexers do not need a second parsing copy for already parsed events.
Indexers first parse raw syslogDeploy the TA to those indexers and the full app to the search head.
ClustersUse the search head cluster deployer for the app and the indexer cluster manager for parsing configuration where needed.

The TA has no Python lookup or dashboards. The search head distributes the app's search-time knowledge through the search bundle. Installing the TA on an indexer does not repair a missing search-time lookup script. Neither package creates an index, opens a network listener or configures forwarding.

Both packages share one source repository so their raw parsing settings stay aligned. They have separate versions and archives. The eye-and-VM icon identifies the app; the beacon-and-VM icon identifies the ingestion TA.

Configure the TA on a heavy forwarder

The TA has no setup screen or credentials to enter. Install TA-vmware-vision 1.0.2 on the HF that first parses the raw records. Keep collection inputs and forwarding in your managed collection app. This example assumes a syslog collector writes separate files on that HF.

  1. Create or select the destination index on the indexing tier. The example uses vmware. Set retention and search-role access for your environment.
  2. Make sure the Splunk service account can read the collector files. Add only the required monitors to your collection app's local/inputs.conf, replacing the paths below.
  3. Check the HF's existing outputs.conf or indexer discovery configuration. It must forward to the intended indexing tier with your site's transport settings. The TA does not configure forwarding.
  4. Verify the effective input and parsing settings, then apply any required restart through your normal deployment process.
[monitor:///var/log/remote/vcenter/*.log]
index = vmware
sourcetype = vmware:vision:vcenter
disabled = 0

[monitor:///var/log/remote/esxi/*.log]
index = vmware
sourcetype = vmware:vision:esxi
disabled = 0

[monitor:///var/log/remote/aria/*.log]
index = vmware
sourcetype = vmware:vision:aria
disabled = 0

Run these checks as the Splunk service account on the relevant HF:

/opt/splunk/bin/splunk btool inputs list --debug
/opt/splunk/bin/splunk btool outputs list --debug
/opt/splunk/bin/splunk btool props list vmware:vision:vcenter --debug

The packaged examples under TA-vmware-vision/README/examples/ are disabled until adapted and enabled. Choose file monitoring or a suitable listener for each stream; using both can duplicate records. If a UF monitors the collector files, place its inputs on the UF and the TA on the first full parsing tier downstream. Do not edit the TA's default files or add another listener on a port already used by the collector.

Follow the complete TA configuration guide for input choices, index placement, forwarding and acceptance checks. TA 1.0.2 changes the icon and documentation; parsing behavior is unchanged, so this update does not require reindexing or rebuilding models. See Splunk's file monitoring documentation for input options.

Install and check the first records

  1. Record the data path. Identify where raw events are first parsed, which indexes will hold them and which roles may search them. Back up an existing app's local settings before upgrading.
  2. Install the release archives on the appropriate tiers. Use Apps → Manage Apps → Install app from file for a standalone or independent search head. Use your normal deployment process for managed and clustered systems. The GitHub source ZIP is not a Splunk install package.
  3. Create or select the destination index. Do this on the indexing tier through your existing configuration management. Preserve retention and access rules. The guides include separate standalone and clustered index examples.
  4. Configure collection. Assign vmware:vision:vcenter, vmware:vision:esxi or vmware:vision:aria to the matching stream. Use vmware:vision:json for the supported JSON event format. Examples are disabled until an administrator adapts and enables them.
  5. Set the search scope. Open Settings → Advanced search → Search macros, select the VMware Vision app and edit vmware_vision_indexes. Keep the definition explicit, such as (index=vmware OR index=vmware_syslog).
  6. Check a short time window. Confirm timestamps, origin, sourcetype and parsed fields against the original messages before widening the dashboard range.
index=vmware sourcetype=vmware:vision:*
| table _time host vcenter event_type record_kind parser_status
        vm_name vmware_action action status user
| head 50

The index macro does not grant permission to search an index. The search user and any scheduled-search owner still need access. If an existing collector uses different sourcetypes, plan the mapping carefully; renaming an existing sourcetype can affect other installed content. The repository includes an example for applying the parser to an existing sourcetype.

Set up the VMware data models

The custom VMware_Vision model has an Events root with detailed fields and child datasets. VMware_Vision_Activity has a smaller Activity dataset for aggregate trends. Both use the VMware index macro. Neither needs Splunk_SA_CIM or its setup page.

First check model membership without acceleration:

| datamodel VMware_Vision Events flat strict_fields=false
| table _time vcenter vm_name event_type vmware_action status
| head 30

If this returns nothing, investigate the source records, time range, index macro, permissions and parser output. Enabling acceleration cannot repair an empty or incorrectly scoped model.

For aggregate dashboards, open Settings → Data models, select VMware Vision Activity, then Edit → Edit Acceleration. Enable it and choose a summary range that fits your searches and capacity. A seven-day range is a reasonable example to evaluate, not a universal setting. Leave the larger detailed model unaccelerated unless a measured workload needs it.

| tstats summariesonly=true count
  FROM datamodel=VMware_Vision_Activity.Activity
  WHERE earliest=-24h latest=-1h
  BY Activity.vmware_action Activity.status

Compare this with the same query using summariesonly=false over a completed, covered interval. Summary-only searches omit unsummarized data. A model showing 100% completion is useful status information, but it is not proof that all expected source events are in scope.

On Accelerated Activity, choose the filters and click Submit. “Search is waiting for input” before submission is a dashboard input state, not an acceleration error. A panel containing only stats sum(events) AS events depends on the dashboard's base search; it is not intended to run alone.

The compact model deliberately omits raw messages and VM identity. Use it for counts and trends. Use VM History and the detailed searches for the exact last recorded change to a VM.

CIM and Enterprise Security

Install Splunk_SA_CIM on the search tier if you need its models. In Enterprise Security, use the CIM version supported by that ES deployment instead of independently replacing it to match a lab.

Version 1.1.1 maps explicit login outcomes into Authentication and selected VM change outcomes into Change. It preserves the original VMware operation in vmware_action. The shared action field uses CIM values for eligible records.

Recorded eventVMware operationCIM result
Successful VM power-onpower_onChange: action=started, status=success
VM reconfigurationreconfiguredChange: action=modified, configuration change
Explicit failed loginlogin_failedAuthentication: action=failure
Power-on request, logout or generic diagnosticRetained as the applicable native operationExcluded from these initial CIM mappings

Alarms, permission changes and host or datastore events remain available in the app but are outside this initial CIM scope. Missing client IP addresses, commands and before/after values are not invented. For a VM change, object is the VM name and object_id prefers its UUID, then its managed object ID. Correlate that ID with the vCenter origin.

  1. Open the CIM app's setup page at /en-US/app/Splunk_SA_CIM/cim_setup.
  2. Add the VMware indexes to Authentication and Change's index allowlists. Preserve indexes already required by other sources.
  3. If using the macro editor instead, update cim_Authentication_indexes and cim_Change_indexes in the CIM app. Their definitions are SPL expressions; an index picker expects only index names.
  4. Check tag matching and model membership before enabling or rebuilding CIM acceleration.
| datamodel Authentication Authentication flat strict_fields=false
| search sourcetype=vmware:vision:*
| stats count by action app

| datamodel Change All_Changes flat strict_fields=false
| search sourcetype=vmware:vision:*
| stats count by action status change_type

Run those as two separate searches. The VMware macro and the two CIM macros are separate scopes. Installing CIM does not connect every index automatically, and enabling CIM acceleration does not enable VMware Vision Activity. Check each ES detection's required datasets and fields before using it with these events.

Upgrades and common problems

1.1.1 update: The CSV lookup now quotes the three input keys in each returned row. This fixes missing parser fields on records with leading or trailing whitespace without changing the stored event. Explicit ESXi Hostd logout records are recognized as events; routine Envoy access logs and known UI/SPS messages are diagnostics. An HTTP 200 response does not prove that a VM operation completed. Logout remains excluded from the initial CIM Authentication mapping.

Upgrade the full app on the search tier. TA 1.0.2 is unchanged. Start a fresh search and check parser_version=1.1.1 on every peer. Setup and Coverage labels absent lookup results lookup_missing; unclassified means the parser ran but did not recognize the record. Rebuild affected accelerated summaries during a suitable maintenance window if historical results need the corrected fields. No reindexing is required.

CRLF was an additional synthetic edge-case test; it is not required by the app, and no VMware or Splunk collection setting was changed to use it. The reported production failure involved trailing whitespace. One limitation remains: events containing embedded CRLF line breaks did not match in the lab's scripted lookup, despite exact byte preservation in the CSV round-trip test. Single-line whitespace and embedded LF cases passed. If your collector combines records using CRLF, validate those samples before relying on this version. The troubleshooting guide records the tested scope.

When upgrading from 1.0.x, change custom native-action filters such as action=power_on to vmware_action=power_on. The bundled dashboards already use the new field. Review local lookup output lists and local model definitions, because they can override the new defaults. Rebuild enabled model summaries after the schema or mapping changes. Raw events do not need reindexing for these search-time changes.

If the lookup works inside VMware Vision but fails in Search & Reporting, inspect sharing and the search bundle before changing Splunk versions. The automatic props rule, transform and searchscripts/vmware_lookup.py metadata must all be visible in the search context. The parser and CIM module must travel with the script. A stale local override can survive an app upgrade.

/opt/splunk/bin/splunk btool transforms list vmware_vision_normalize --app=vmware_vision --debug
/opt/splunk/bin/splunk btool props list vmware:vision:vcenter --app=vmware_vision --debug

A second problem is less obvious: filtering a search on a computed value that is not present in the raw log. The package declares INDEXED_VALUE=false for relevant derived fields so Splunk does not discard valid records before normalization. Some of those fields, such as action and status, are shared names. Their exported metadata can increase search work for other sources too; keep index and time scopes narrow and measure the cost.

Missing VM identity on a service diagnostic is expected. Missing identity on a known VM event deserves a closer look at the original message, forwarding format and parser result. Setup and Coverage is intended to help separate those cases.

Build and validation

The source tree follows the same build sequence used for the other Splunk projects: build from source, verify the generated app, package it, calculate checksums and run AppInspect. UCC 6.6.0 builds the configuration page. AppInspect 4.3.1 checks the resulting archives. The parser itself uses Python's standard library.

git clone https://github.com/majidershadi/vmware-vision.git
cd vmware-vision
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-build.txt
make release

Use Linux or WSL with Python 3.10 or newer, GNU Make and Git. The repository's build guide explains each step and the output files. Development tools, test fixtures, credentials and local settings stay outside installation packages. Public source tests remain available so behavior can be reproduced and reviewed.

The standalone functional checks used Splunk Enterprise 10.4.1 and CIM 8.7.0. A set of sixteen synthetic records produced one Authentication record, eleven Change records and four exclusions. Both custom models returned the expected event set. These checks establish specific behavior, not production throughput or compatibility with every ES detection.

The runtime declarations cover Python 3.9 and 3.13, with a 3.9 fallback for earlier configuration handling. Splunk 10.0.2 remains a compatibility target, not a completed distributed acceptance test. Local AppInspect results do not imply Splunkbase approval. Validate the actual collection route, search peers, event volume and summary coverage before relying on the deployment.

The project is published under Apache 2.0. For setup details, use the installation guide, data-model guide and CIM guide. Report parser issues with a sanitized event, the expected result and the app and Splunk versions.
